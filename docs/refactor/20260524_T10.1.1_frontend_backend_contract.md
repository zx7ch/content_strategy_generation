# T10.1.1 Additional Contract: WorkflowRun Frontend/Backend Interaction

日期：2026-05-24

适用范围：Creator Workbench 的 workflow-v2 / WorkflowRun 链路。本文是 T10.1.1 的追加 contract，用于约束后端执行分发、SSE/snapshot 返回、前端进度卡片和聊天 timeline 的边界。

## 1. 核心原则

1. `workflow_runs` 和 `workflow_steps` 是任务状态唯一真相。
2. `workflow_events` 只用于 SSE、回放和审计，不作为当前状态唯一真相。
3. 前端恢复当前任务必须先读 snapshot，再订阅 events。
4. 后端任务执行只能影响 WorkflowRun 状态、events、artifacts 和最终 result message，不能在执行过程中不断写普通 assistant chat message。
5. 前端只在任务进度卡片内展示执行进度。除最终 `artifact_result` 外，后台 step 进展不得刷屏到聊天 timeline。
6. `step_failed` 表示单个 step 失败或待重试，不等于整个 run 失败。只有 `run_failed` 才能把任务卡片标记为整体失败。
7. `cancelling`、`cancelled`、`failed`、`succeeded` 状态的旧 run 不能再接收 `add_constraint`。用户在历史窗口再次输入新的创作请求时，应启动新的 run。
8. Workflow-bound jobs 必须可以脱离 legacy session row 执行。旧 session/job API 保留给历史路径，不参与 workflow-v2 当前状态判断。

## 2. 后端接口与返回契约

### 2.1 `POST /threads/{thread_id}/messages`

用途：保存用户消息，并由后端 intent router 判断是启动新 workflow、补充约束、查状态、暂停/恢复/取消，还是普通对话。

返回必须包含：

```json
{
  "message": {},
  "assistant_reply": {},
  "intent": "start_workflow | add_constraint | ask_status | pause_workflow | resume_workflow | cancel_workflow | free_chat",
  "active_run_snapshot": null,
  "command_result": null
}
```

当 intent 为 `start_workflow`：

- 后端必须创建 `workflow_run`。
- 后端必须初始化 canonical `workflow_steps`。
- 后端必须 enqueue 第一个 `pending/retrying` step job。
- 返回的 `active_run_snapshot` 必须包含 `run_id`、`status`、`phase`、`current_step`、`steps`。
- `assistant_reply` 可以是简短确认，例如“已开始新的创作任务。”，但它不是进度承载体。

当 intent 为 `add_constraint`：

- 仅允许 active run 状态为 `running` 或 `paused` 时写入约束。
- 后端写入 `workflow_constraints`，并返回最新 snapshot。
- 前端展示用户消息和简短确认，不新建任务卡片。

当 active run 为 `cancelling/cancelled/failed/succeeded`：

- 不允许把新消息路由成 `add_constraint`。
- 如果文本命中创作启动意图，必须路由成 `start_workflow` 并创建新 run。
- 如果文本只是普通追问，路由成 `free_chat` 或 `ask_status`，不得抛出 500。

### 2.2 `GET /workflow-runs/{run_id}/snapshot?thread_id={thread_id}`

用途：恢复和校准前端任务卡片。

返回必须包含：

- `run`: `run_id`、`thread_id`、`status`、`phase`、`current_step`、`started_at`、`completed_at` 等。
- `steps`: 所有 canonical steps，按执行顺序返回，包含 `step_id`、`step_name`、`phase`、`status`、`attempt_count`、`started_at`、`completed_at`。
- `artifacts`: 已提交 artifacts。
- `constraints`: 当前 run 的约束。
- `active_jobs` 或等价字段：当前正在执行或排队的 workflow-bound job。

前端必须从 `steps` 计算：

```text
completed_steps = succeeded/skipped terminal steps
total_steps = steps.length
percent = floor(completed_steps / total_steps * 100)
current_step = running step > first pending/retrying step > run.current_step
```

### 2.3 `GET /workflow-runs/{run_id}/events`

用途：SSE 订阅和断线回放。

约定：

- Event payload 可以没有 `message`。
- 前端必须根据 `event.type` 和 `payload.step_name` 映射用户可读文案。
- EventSource 重连必须关闭旧连接，不得为同一 run 创建多个并发订阅。
- 前端收到 event 后可以节流刷新 snapshot，不能每个渲染周期都请求 snapshot。

关键事件语义：

| Event type | 后端含义 | 前端展示 |
| --- | --- | --- |
| `run_created` / `run_started` | run 已创建或开始 | `任务已创建` |
| `steps_initialized` | canonical steps 已写入 | `已拆解创作步骤` |
| `step_started` | 某 step 开始执行 | `正在执行：{step label}` |
| `artifact_attached` | 产物已提交 | `{artifact label}已保存` |
| `step_completed` | 某 step 成功完成 | `已完成：{step label}` |
| `step_failed` | 某 step 失败或待重试 | `步骤遇到问题，正在处理`，不得标记 whole run failed |
| `run_paused` | run 已暂停 | 卡片状态显示暂停 |
| `run_cancelled` | run 已取消 | 卡片状态显示已取消，可隐藏执行按钮 |
| `run_failed` | run 整体失败 | 卡片状态显示失败，只出现一条失败状态 |
| `run_succeeded` | run 整体完成 | 卡片显示完成，并等待 timeline/result hydrate |

### 2.4 Worker / Dispatcher

执行分发契约：

1. start workflow 后，`WorkflowStepDispatcher.enqueue_first_step(run_id)` 必须入队第一个 pending step。
2. worker lease workflow-bound job 时，不能要求 legacy session row 存在。
3. worker 执行 step 成功后，必须通过 `WorkflowRunManager` 完成 step 并写 event。
4. step 成功后，`WorkflowStepDispatcher.enqueue_next_step_or_complete(run_id)` 必须自动入队下一步。
5. 当没有 pending/running/retrying step 时，dispatcher 必须 complete run。
6. run complete 后，后端最多写入一条最终 `artifact_result` assistant message，供 thread timeline 展示最终结果。

## 3. 前端显示契约

### 3.1 聊天 Timeline

聊天 timeline 只展示：

- 用户发送的消息。
- 后端保存的普通 assistant reply。
- 最终 `artifact_result`。
- 读取失败、发送失败等本地 UI 错误提示。

聊天 timeline 不展示：

- 每个 `step_started` / `step_completed` 作为独立 assistant bubble。
- 重试中的 `step_failed` 作为“任务执行失败，请重试。”刷屏。
- snapshot polling 的中间状态。

### 3.2 任务进度卡片

当存在 active run 且状态为 `running/paused/cancelling/failed` 时，前端显示任务卡片。

理想视图：

```text
创作任务进行中
阶段：真实素材搜索
当前：正在搜索小红书真实内容
进度：4 / 18 · 22%

最近进展：
✓ 任务已创建
✓ 已拆解创作步骤
⋯ 正在搜索小红书真实内容

[暂停] [取消]
```

显示规则：

- 标题由 run status 决定：running 显示“创作任务进行中”，paused 显示“创作任务已暂停”，failed 显示“创作任务执行失败”。
- 阶段由 `run.phase` 或当前 step phase 映射。
- 当前由 running step 优先映射；没有 running step 时，用 first pending/retrying step。
- 进度由 snapshot steps 计算，不依赖 event payload 里的 progress。
- 最近进展来自 SSE event type 映射，保留有限条数。
- pause/resume/cancel 按 run status 显示；failed/cancelled/succeeded 不显示不可用操作。

### 3.3 自动滚动与请求节流

- 用户发消息和最终结果可以触发聊天区滚动。
- 任务卡片内部状态更新不得触发聊天区不断下滑。
- 同一 run 同一时间只能有一个 SSE subscription。
- snapshot refresh 必须节流并防重入；不能形成 `/snapshot` 与 `/events` 请求风暴。
- 切换 thread 时必须关闭旧 run 的 SSE subscription，并忽略旧 run 延迟到达的事件。

## 4. 常见用户场景

### 4.1 打开 Creator 页面

触发：

```text
GET /health
GET /workspaces/default
GET /brands
GET /threads
```

前端显示：

- runtime 在线时显示主界面。
- thread list 从后端返回渲染。
- 不启动 workflow。

### 4.2 进入历史 Thread

触发：

```text
GET /threads/{thread_id}/timeline
```

如果 thread 有 active run：

```text
GET /workflow-runs/{run_id}/snapshot?thread_id={thread_id}
GET /workflow-runs/{run_id}/events
```

前端显示：

- timeline 显示历史消息和最终 artifact result。
- 如果 active run 未终态，恢复任务进度卡片。
- 如果 active run 已终态，默认不显示运行中卡片。

### 4.3 新建对话后输入创作请求

触发：

```text
POST /threads/{thread_id}/messages
```

后端：

- 保存用户消息。
- intent router 判断为 `start_workflow`。
- 创建 run、初始化 steps、入队第一步。
- 返回 `active_run_snapshot`。

前端显示：

- 立即显示用户消息。
- 显示简短 assistant 确认。
- 创建并显示任务进度卡片。
- 订阅 `GET /workflow-runs/{run_id}/events`。

### 4.4 后台执行 step

触发：

```text
JobWorker lease queued workflow job
WorkflowStepExecutor execute step
WorkflowRunManager append workflow_events
```

后端：

- `step_started`、`artifact_attached`、`step_completed` 进入 workflow events。
- 成功完成 step 后自动 enqueue 下一步。

前端显示：

- 只更新任务卡片的阶段、当前、进度、最近进展。
- 不追加普通 assistant bubble。
- 不因 task card 更新自动滚动聊天区。

### 4.5 单步失败但 run 未失败

后端：

- 写入 `step_failed` 或 retry 相关 event。
- 如果还有 retry 或 safe boundary，run 仍可保持 running/paused。

前端显示：

- 可以在任务卡片最近进展显示“步骤遇到问题，正在处理”。
- 不显示整任务失败。
- 不向 timeline 追加“任务执行失败，请重试。”。

### 4.6 整体 run 失败

后端：

- 只有确定 run 进入 `failed` 时才写 `run_failed`。

前端显示：

- 任务卡片状态变为失败。
- 最多出现一次失败提示。
- 不重复创建失败 bubble。

### 4.7 用户暂停、恢复、取消

触发：

```text
POST /workflow-runs/{run_id}/pause
POST /workflow-runs/{run_id}/resume
POST /workflow-runs/{run_id}/cancel
```

前端显示：

- pause 后卡片显示暂停，按钮变为恢复/取消。
- resume 后卡片恢复执行中。
- cancel 后卡片显示取消或收起；不再允许向该 run add constraint。

### 4.8 用户在取消后的历史窗口再次输入创作请求

触发：

```text
POST /threads/{thread_id}/messages
```

后端：

- 如果旧 active run 是 `cancelling/cancelled/failed/succeeded`，不得调用 `add_constraint`。
- 文本是创作请求时创建新 run。
- 返回新 run 的 snapshot。
- 不得返回 500。

前端显示：

- timeline 追加新用户消息。
- 显示新的任务卡片。
- 订阅新 run events，并关闭旧 run events。

### 4.9 run 成功完成

后端：

- 所有 steps 成功/跳过后，run 进入 `succeeded`。
- 写入 `run_succeeded` event。
- 写入最终 `artifact_result` message。

前端显示：

- 任务卡片显示完成或收起。
- timeline 显示最终 artifact result 卡片。
- 后续用户新创作请求应创建新 run；用户修改请求可作为 revision/rerun 流程进入后续任务。

## 5. 禁止行为

以下行为视为 contract violation：

- `POST /threads/{id}/messages` 因旧 run 为 `cancelling` 而抛 500。
- start workflow 后没有入队第一步，导致前端只有“已开始新的创作任务。”。
- 前端把每个 workflow event 追加成聊天 bubble。
- 前端把 `step_failed` 当成 whole run failed。
- 前端因 SSE event 或 snapshot refresh 不断自动滚动页面。
- 同一 run 同时存在多个 EventSource，造成 `/events` 和 `/snapshot` 请求风暴。
- workflow-bound job 因缺少 legacy session row 无法 lease/execute。
- run 成功后不写最终 `artifact_result`，导致用户看不到结果。

## 6. 回归测试清单

后端必须覆盖：

- message endpoint 启动 run 后，第一步 job 已入队。
- workflow-bound job 在无 legacy session row 时可执行。
- worker 成功 step 后自动入队下一步。
- 最后一步完成后 run 进入 `succeeded` 并写最终 result message。
- cancelled/cancelling/failed/succeeded run 上的新创作请求会启动新 run，不会走 `add_constraint` 500。

前端必须覆盖或人工验收：

- 新建对话输入创作请求后显示任务进度卡片。
- event payload 无 `message` 时，仍能根据 event type 显示“任务已创建 / 已拆解创作步骤 / 正在执行...”。
- `step_failed` 不会产生聊天刷屏。
- 任务卡片进度变化不会导致页面不断下滑。
- 切换 thread 或开始新 run 会关闭旧 SSE subscription。
- cancelled 历史 thread 中再次输入创作请求，可以启动新 run。
