检索候选
discover		stage_checkpoints: collect_page
保存 query、排序、分页候选。		候选只能藏在检查点 JSON 中；用户无法判断“搜到了什么”。将候选投影为审计读模型：查询词、标题、作者、链接、排名、后续状态。一次运行后可读取全部候选；不暴露 Cookie、token、原始会话。
详情抓取
detail		stage_checkpoints: detail / selection_revision
每次外部调用前后 flush；保留 28 篇详情。		Runtime 重启后无法证明读回同一 SQLite；用户看不到 28 篇详情。增加 Runtime build ID + 实际 DB 绝对路径诊断；为用户提供候选笔记明细与 JSON 导出。停止并重启冻结 Runtime 后，相同 run 仍读到 28 篇详情。
筛选 / 准入direction_source_projections、directional_evidence_packets
保存 selected、原因、query hits 和安全字段。		“相关 0 / 准入 0”只有汇总，无法判断筛选是否合理。用户侧证据审计页：入选/排除原因、详情状态、检索词；证据不足报告中直接引导打开。用户可独立复核每篇笔记为何被排除或未准入。
报告 / Traceresult_snapshots、publication、observation_events
Trace API 有意脱敏 payload。		Trace 缺少可理解的筛选过程；开发者无法确认实际运行哪个包、使用哪个 DB。双层观测：用户看脱敏筛选过程；开发者看 build、DB 路径、数据库更新时间和操作摘要。/health 与启动日志均能标识同一 Runtime 与同一 DB。
返回 checklist / 结束当前 end_content_research 会删 workflow、brief、Trace 与基础证据；部分新表反而遗留为孤儿。修改方向会不可逆地丢失可见证据；又留下无法通过产品访问的残余数据。改为永久归档：清除活动入口，不删除 run 数据。另设二次确认的“永久删除”，事务覆盖全部关联表。归档后历史仍可查看/导出；永久删除后所有关联表均无该 run。

两个视角，各自解决的问题

用户功能：证据审计

  • 入口：报告和侧栏的“查看候选与筛选”。
  • 展示：标题、作者、链接、检索词、详情状态、入选/排除原因。
  • 价值：用户能判断“系统筛掉得是否合理”，而不是只能接受“证据不足”。
  • 导出：JSON 是辅助能力，不替代页面审计。

开发者 Observation：运行诊断

  • 启动与健康检查：build ID、Runtime 版本、最终 SQLite 绝对路径、DB 修改时间。
  • 执行：每个 provider 操作的次数、耗时、错误代码与持久化检查点。
  • 边界：不向 UI 泄露 Cookie、API Key、token、原始登录会话。
  • 价值：能定位“旧包 / 错误 DB / Worker 与 API 不一致”。

最小化活动配置

# LLM 与小红书登录由 Creator 右栏保存到本机 SQLite。 LOG_LEVEL=INFO

文件可为空；该行仅保留运行日志可读性。

升级迁移规则

  • 先创建带时间戳的旧配置备份。
  • 生成最小活动配置；不再加载 API Key、Cookie、模型、DB 路径、RAG/V2/告警/生成参数。
  • Runtime 强制拥有内部存储路径；UI 保存的模型与登录态仍在 SQLite。
  • 启动后以 health 诊断确认迁移后的实际库。

发布门禁：必须同时通过

冻结包真实重启测试：携带旧配置启动 → 创建一轮包含详情候选的调研 fixture → 停止 Runtime → 重启同一包 → 读取相同 run 的候选、Trace、报告 → 归档后仍可读 → 显式永久删除后所有关联表与 API 均不可读。
