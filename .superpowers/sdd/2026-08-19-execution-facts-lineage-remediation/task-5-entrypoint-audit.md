# Task 5 entrypoint audit — Scope and report mutation authority

Audit base: `0af2472` (`feat(creator): enforce server-owned scope recovery`). Read-only code audit; no production code was changed.

## Verdict

Task 5 still has two authority defects and one test-proof defect:

1. Restored Draft confirmation is rendered from browser-inferred state rather than the projected `confirm_scope` command.
2. Legacy report repair and model/collection recovery controls are not all driven by projected actions. The backend blocks most legacy retry/resume attempts once Scope lineage exists, but packet repair can mutate relevance/admission before it reaches the later Scope guard.
3. The new browser journeys mock the exact `/scope` and `/actions` seam they are meant to prove. Backend execution-unit coverage is strong, but there is no real-stack browser proof for the Task 5 authority contract or same-run/cross-run races.

The smallest useful seam is one server-owned `WorkflowMutationAuthority` module whose interface both projects and requires an action. `run_workflow_action` must call it before dispatching any mutator; `get_scope_projection` must serialize the same decisions; Creator must render commands only from those rows. This is a deep module with one policy implementation, not a broad report/worker refactor.

## Recommended small seam

Add one module, for example `app/content_research/workflow_mutation_authority.py`, with a small interface:

```python
class WorkflowMutationAuthority:
    def project(self, workflow_run_id: str) -> list[ProjectedWorkflowAction]: ...
    def require(self, workflow_run_id: str, action: str, payload: Mapping[str, object]) -> ProjectedWorkflowAction: ...
```

Its implementation can reuse the existing Scope projection inputs, runtime snapshot, report recovery projection, and execution facts. It should own these rules:

- `confirm_scope`: available only for the exact persisted Draft command.
- `resolve_coverage`: available only for the open snapshot and one available resolution; a failed-unit replay must byte-for-byte match the projected replay request.
- `start_formal_research`: available only for the confirmed initial eligible lineage.
- `retry_formal_research`, `resume_formal_research`, `repair_from_persisted_packets`: available only when explicitly projected from durable runtime/report facts and no pending Coverage or execution unit owns recovery.
- Unknown/manual outcomes project no mutating action.

Call `require(...)` in `run_workflow_action` immediately after loading the workflow and before any branch at `service.py:3230`. This closes repair's pre-guard writes and makes raw HTTP callers obey the same contract as Creator. Keep `_require_scope_execution_authority` and lease fencing as defense-in-depth domain/worker guards.

Serialize `project(...)` from `get_scope_projection`, then add a tiny frontend selector such as `availableWorkflowAction(projection, name)`. Use it for confirmation, report repair, model recovery, Trace recovery, initial start, and legacy retry/resume. Do not let individual cards derive mutation authority from `state`, Trace, report reason, or LLM fields.

## Minimum tests for the fix

1. JSDOM: restored Draft with missing/unavailable `confirm_scope` renders no confirm button; available exact command does.
2. Backend real router: every action sent while an execution unit is `running`, `outcome_unknown`, or manual-recovery is rejected before any checkpoint/admission/task/report row changes, except exact projected replay.
3. Packet repair negative: execution-unit-owned evidence-only report produces zero row deltas.
4. Real Playwright/app/router/provider-fake journeys for all three Coverage decisions, known retry (same unit, next attempt, one publication), unknown outcome (no command), and Draft restore.
5. Deterministic same-run out-of-order Scope/Trace/report responses and cross-run races for all three channels, not Scope alone.
6. Public response assertion: resolution result omits `execution_authorization` and exposes only the safe execution-unit projection.
